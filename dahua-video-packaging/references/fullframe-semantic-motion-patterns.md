# 开放式语义视觉生成

本文件用于视觉规划和验收。目标不是从动画菜单里挑效果，而是先理解口播，再现场生成最合适的图形、动画、模拟界面、信息图、视觉隐喻或素材。

## 总原则

固定大华的黑黄视觉身份、人物构图、字幕安全区、可读性和同步规则；开放具体视觉表达。已有组件、图表和动作模式只是积木与推理示例，不是白名单，也不是每条视频必须凑齐的类别。

固定推理链：

`口播文案 → 理解语义结构 → 构思视觉模型 → 复用积木或生成新结构 → 设计必要运动 → 验证理解增益`

先回答三个问题：

1. 观众此刻真正难理解的是什么？
2. 哪些对象、关系或变化如果被“看见”，理解会更快？
3. 这个画面比纯字幕或文字卡片具体多提供了什么？

第三问没有明确答案时，回退到文字卡片或纯字幕。

## 双删除测试

视觉方案完成前必须连续做两次删除测试：

1. **删除整个包装**：如果只看人物和字幕，观众仍能得到同样的关系、过程或判断，说明包装只是复述，直接删除。
2. **只删除运动**：如果保留最终静态图形后，观众仍能得到同样理解，说明运动没有语义作用，改为静态图解。

不得用“强调重点、丰富画面、增强节奏、提升质感”作为理解增益。这些是表现效果，不是语义增量。

包装的出现时间也属于必要性判断。先说结论、后说关系时，结论阶段可以只有字幕；直到具体对象或关系被口播引入，图形才出现。不得用一张与字幕近义的标题卡提前占位。

典型反例：口播开头说“执行强的人不一定适合当负责人”时，再显示“执行强 ≠ 适合当负责人”，只是把字幕压缩一遍，应当保持纯字幕。直到口播进入“自己拿结果”和“带一群人拿结果”的具体差异时，才允许出现一个结果向多个团队节点分发的图形；如果该图形仍不能增加理解，也继续只用字幕。

## 语义建模扫描

逐段识别下列语义维度。它们是思考维度，不是组件目录：

- 数量、比例、排名、趋势、速度、差距和阈值；
- 一对一、一对多、多对一、层级、网络、上下横向和空间方向；
- 步骤、机制、因果、分支、循环、反馈和瓶颈；
- 增长、减少、积累、损耗、替代、筛选、迁移和前后状态；
- 责任、经验、信息、资源、风险等抽象对象的归属和流动；
- 工具操作、真实行为、人物状态和工作场景；
- 难以直说的抽象概念，可否用容器、路径、开关、齿轮、桥梁、漏斗、地图或其他视觉隐喻解释。

每个候选段先写：

- `semanticIntent`：观众需要理解的结论或关系；
- `understandingGain`：删除整个包装后会丢失的具体理解；
- `whyNow`：为什么在这一句或这个词组开始出现，而不是更早；
- `visualModel`：画面里有哪些对象、如何组织、发生什么变化；
- `whyThisVisual`：它为何比纯文字更快、更准或更省解释；
- `motionPlan`：哪些变化必须通过运动呈现，或为什么保持静态；使用语义动画时另写 `motionGain`，说明删除运动会丢失什么。

## 开放生成范围

允许直接创建新的 SVG、CSS 图形、HTML 结构、数据面板、图表、表格、微型模拟器、界面演示、系统图、物体动画和视觉隐喻。`component` 与 `motionPlan.pattern` 可以使用新的 kebab-case 名称，不要求命中既有列表。

可复用现有积木，也可组合或重构。判断标准不是“以前有没有这个组件”，而是：

- 是否与当前口播一一对应；
- 是否让关键关系无需额外说明就能看懂；
- 是否保持黑黄视觉身份、安全区和字号底线；
- 是否在当前时长内读得完；
- 是否能稳定渲染并通过最终 MP4 抽帧检查。

新结构不因“新”而自动高风险。只有改变固定视觉身份、侵入人物字幕安全系统、需要大面积长期接管或存在明显渲染不稳定时，才进入风险预览。

## 推理示例，不是菜单

- “数量提升”可以是柱长变化，也可以是对象堆积、容器填充、数字计数、刻度越线或空间占比变化；按语义选择，不固定为柱状图。
- “责任从老板转给负责人”可以让任务令牌迁移、控制权切换、连接线改道或角色容器重新归属；重点是观众看见“归属改变”。
- “经验沉淀为组织能力”可以让零散经验汇入档案库、形成 SOP 再复制到团队，也可以表现为反复归零被稳定存储取代；重点是从个人短期状态变为组织可复用状态。
- “上下协同、横向拉通”可以使用中心角色和多方向连接，也可以用空间分层、桥接通道或共享工作台；重点是方向与职责关系。
- “47%”“100 字 vs 错几十字”可用数字面板、比例占位、误差散点、对比容器或识别界面；数据形式应服务于这一句的判断，不复制参考片的固定画法。
- 工具操作、人物行为或现场状态若真实画面最直接，可使用自录、品牌官方、定制生成或许可清楚且语境匹配的 B-roll。

禁止把上述名词抄成新的可选组件表。每次都要从口播重新推理视觉答案。

## 合格语义运动

语义动画至少让一个可识别对象发生位置、归属、状态、数量、路径或结构变化，而且这种变化对应口播含义。常见关系包括流动、转移、替代、划除、分流、汇聚、反馈、前后变化、累积和筛选，但允许创造任何更贴切的新模式。

在 `motionPlan.pattern` 中写描述性的 kebab-case 名称，例如 `responsibility-handoff`、`experience-to-system` 或 `threshold-crossing`。名称只是记录，动画质量取决于对象与语义的映射，不取决于是否命中示例词。

以下只算基础转场，不能单独填写为 `semantic-motion`：

- 整张卡淡入、上移、缩放或滑入；
- 文字节点依次出现；
- 标题居中后让位；
- 普通箭头线条被画出来，但没有对象沿关系移动或发生状态变化；
- 关键词变色、发光、轻微呼吸或装饰性漂移。

若动画必须依赖额外口头解释才看得懂，说明视觉映射不成立；重构视觉模型，或回退到清楚的文字卡片。

同一条视频中出现结构完全平行的连续表达（例如多组“第一性原理是……不是……”）时，先确定整组统一的包装语法：要么每组都在答案与否定项处使用同构的语义运动，要么整组都保持静态／纯字幕；不得随机只动画其中几组。若选择语义运动，`actors` 中的每个关键对象都必须有可见事件并参与位置、状态、路径或归属变化，禁止一部分对象完成动画、另一部分仅作为静态贴图挂在卡片中。

## 时间轴写法

自定义语义视觉：

```json
{
  "component": "experience-to-system",
  "understandingGain": "让观众看见经验从个人归属转成团队可复用资产",
  "whyNow": "从口播说到经验沉淀时开始，前面的观点句只保留字幕",
  "visualModel": "零散经验令牌汇入档案库，形成SOP后复制到团队节点",
  "whyThisVisual": "让个人经验变成组织资产的过程可见，而不是只重复结论",
  "motionPlan": {
    "mode": "semantic-motion",
    "semanticIntent": "个人经验被沉淀并转化为团队可复用能力",
    "pattern": "experience-to-system",
    "actors": ["经验令牌", "档案库", "SOP", "团队节点"],
    "motionGain": "令牌的归属变化让个人经验转成组织能力的过程可见"
  }
}
```

保留静态卡片：

```json
"motionPlan": {
  "mode": "static",
  "semanticIntent": "强调单一判断",
  "reason": "没有对象关系或状态变化，运动不会增加理解"
}
```

B-roll：

```json
"motionPlan": {
  "mode": "b-roll",
  "semanticIntent": "直接展示真实复盘操作",
  "pattern": "real-review-action",
  "actors": ["复盘表格", "操作者"]
}
```

卡片数不少于 `6` 的完整视频，若所有 `motionPlan` 都是 `static`，视为语义建模扫描失败。只有用户明确要求全静态时，才允许在时间轴顶层记录：

```json
"motionPolicy": {
  "staticOnlyApproved": true,
  "reason": "用户明确要求全片只使用静态文字卡片"
}
```
